## Context

肉鸽旅途2文档仓库当前有10个 Markdown 文件，其中6个超过项目规范的200行上限（最高418行）。每个文件混合了设计规范、配置数据和校验信息，导致：

- 修改卡牌数值时需要翻阅包含设计理念的文件
- 无法独立定位"规则"和"数据"
- 后续子系统加入时会进一步膨胀

拆分维度已在探索阶段确认：规范 / 数据 / 校验（或架构）。

## Goals / Non-Goals

**Goals:**
- 所有文件控制在200行以内
- 每个文件职责单一（规范 OR 数据 OR 校验）
- 建立可复用的拆分范式，供后续子系统参照
- 保持所有游戏设计内容零丢失

**Non-Goals:**
- 不新增游戏设计内容
- 不改变文档编号体系（00_总纲、01_核心战斗等）
- 不调整 `.codebuddy/` 下的 OpenSpec 配置
- 不处理尚未编写的子系统（商店、事件、奖励等）

## Decisions

### D1: 拆分粒度——按"内容性质"而非"字数"

选择将每个超标文件按内容性质拆分（规范/数据/校验），而非简单按字数均分。

**理由**: 按内容性质拆分后，每个文件有明确的维护场景。规范文件几乎不改动，数据文件频繁更新，校验文件在平衡性调整时使用。

**备选**: 按字数均分（如418行拆为2个209行）——不采用，因为会破坏语义完整性。

### D2: 敌人配置使用子目录

敌人数据按等级拆为"普通敌人.md"和"精英与Boss.md"，放在 `01_核心战斗/敌人配置数据/` 子目录下。

**理由**: 敌人数量后续会大幅增加（设计文档提到"待配置"占位），子目录可容纳未来扩展而不膨胀目录列表。

**备选**: 所有敌人数据放在一个文件——不采用，预计最终会超过200行。

### D3: 遗物按稀有度分文件

普通遗物和稀有遗物分开，因为获取途径、触发频率、设计约束差异较大。

**备选**: 按功能类型分（攻击/防御/辅助）——不采用，稀有度是设计层面的核心分界线。

### D4: 不移动文件到新的编号目录

所有拆分后的文件保留在原编号目录下（如卡牌数据仍在 `01_核心战斗/`）。

**理由**: 拆分是为了控制粒度，不是为了重组层级。当前层级（00~04）已经反映了系统边界。

## Risks / Trade-offs

- **文件数量增加（10→20）** → 通过统一的命名规范和目录结构补偿，每个文件名即说明其职责
- **跨文件引用需要更新** → 拆分时同步更新所有内部链接
- **拆分边界可能有争议** → 以原文件中的二级标题（##）作为自然边界，减少主观判断
